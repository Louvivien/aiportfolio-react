# Annual portfolio performance

The original dashboard keeps one performance badge. It defaults to the Paris
calendar year and can show another year selected in “Gérer la performance
annuelle”. Other historical P/L indicators and the symbol-based position model
are unchanged. `/api/performance/2026` remains compatible with existing exports.

## Calculation

The year is a parameter (2026–2100), not a hardcoded result. Opening capital is
securities valued on December 31 of the preceding year plus opening cash. The
XIRR initial outflow is dated January 1. External deposits and promotional credits
are negative investor cash flows; external withdrawals and the terminal value
are positive. Effective return is `(1 + annualized XIRR)^(elapsed days / 365) - 1`.
EUR gain is `final - initial - deposits + withdrawals - promotions`.

Trades, internal transfers, dividends, interest, fees and taxes are never added
to the external-flow list used by XIRR. Their effect is already in securities
and actual cash balances. Promotion capital is excluded from investment gains.
Historical realized P/L is independent of this calculation.

Missing numeric inputs produce no fabricated return. Assumptions and completeness
remain in the management view and JSON audit; the dashboard retains its single
plain badge. The first day and unsupported/non-unique XIRR patterns can display a
gain with an unavailable percentage. Actual/365 is retained for leap years.

## Annual records and cash

`performance_years` is keyed by numeric year, with an optimistic `revision`,
input data, opening snapshot, optional closing snapshot/report and cash financial
fingerprint. `performance_history` records before/after versions transactionally.
`performance_inputs` remains untouched as the legacy 2026 source/archive.

Cash is manually confirmed as one consolidated EUR total, including its date.
It must be dated consistently with the current valuation. The application does
not infer cash from incomplete broker histories, carry a closing cash balance
forward as current cash, or automatically add deposits to an already inclusive
balance. Changes to recorded financial positions or external flows require cash
confirmation. Quote/name/fundamental refreshes do not invalidate cash.

Flow edits require valid dates in the year, positive integer cents, unique IDs,
a type and explicit internal/external classification. EUR conversion, if needed,
must be performed before entering a flow. The scope is inherited; the existing
NVIDIA inclusion and SOXL exclusion are preserved. This version does not provide
a broker-account model or an automatic cash ledger.

## Closing a year

“Préparer [next year]” creates an empty draft. It does not guess future holdings,
prices, cash or performance. From January 1 onward, a closing preview can be built
from recorded lots at December 31 and a confirmed cash balance. Historical prices
are chosen on or before the valuation date (maximum seven-day lookback), never
from future/live prices. Actual quote dates, historical FX dates/rates and each
position's contribution appear in the preview for review. Unknown quantities,
quotes or FX prevent complete valuation. The stricter, previously reconciled
2025 opening-price policy is preserved during migration.

Previews are server-generated, expire after 30 minutes, and bind the annual
revision, next-year revision and financial position fingerprint. Committing a
close verifies those values in a MongoDB transaction, freezes the report and
positions used for audit, and copies that exact snapshot into the next opening.
No external flow is generated by rollover. A closed year is read independently
of subsequent changes to live holdings or quotes.

A correction requires reopening the year. Its prior version remains in history;
the successor's opening is marked for review and its return suppressed. A new
preview requires explicit consent to replace the successor opening. Already
closed successors must be reopened from newest to oldest first. There is no
silent cascading rewrite. No scheduled job or December 31 login is required.

## API

- `GET /api/performance/:year`: calculated or frozen report.
- `GET /api/performance/:year/manage`: inputs, snapshots and available years.
- `GET /api/performance/:year/audit`: reproducible inputs, values and change history.
- `PUT /api/performance/:year/inputs`: `{ revision, patch }`.
- `POST /api/performance/:year/prepare-next`: `{ revision }`.
- `POST /api/performance/:year/close-preview`: `{ revision, cash_eur }`.
- `POST /api/performance/:year/close`: `{ preview_id, update_next_opening }`.
- `POST /api/performance/:year/reopen`: `{ revision }`.
- `GET /api/performance/:year/reconciliation`: retained accounting evidence.

These endpoints use the application's existing access model. The snapshot and
performance values themselves cannot be edited through the inputs endpoint.

## Migration and validation

Run from `backend`: `node scripts/migrate-annual-performance.mjs` for a preview,
then `node scripts/migrate-annual-performance.mjs --apply`. The migration is
idempotent, backs up financial source data with restricted file permissions,
checks concurrent edits and preserves 2026 flows, cash and all positions. It
freezes the reconciled opening inventory and prices, not a hardcoded return.

`npm test` covers financial logic. `node scripts/test-annual-lifecycle.mjs` uses
an isolated disposable Mongo database to exercise conflict handling, cash review,
closing, correction propagation, audit history and transaction atomicity; its
test documents are removed afterward. Frontend tests and browser interaction
checks cover the badge, editor, flow/cash forms, year selection and JSON download.
